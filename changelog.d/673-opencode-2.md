### Added
- OpenCode 2 (`@opencode/cli`) is supported, through the same `opencode` host and one plugin for both versions (ADR-040): OpenMoat's plugin exports `{ id, server, setup }`, so OpenCode 1 (1.3.4 and later) runs it on `tool.execute.before` and OpenCode 2 on `execute.before`, and an upgrade from 1 to 2 needs no new `openmoat init`; `openmoat status` and `openmoat doctor` name the hook the `opencode` on the search path runs. On OpenCode 2 an `ask` is OpenCode's own permission prompt (OpenCode 1 still receives it as a deny with the `openmoat allow --last` hint), and the plugin replaces the call's `tool` and `input` with what it checked, frozen, so another plugin that rewrites the call afterwards makes it fail; the shell command it checked is pinned the same way when OpenCode starts it. OpenCode 2's tools (`shell`, `read`/`write`/`edit` with `path`, `patch`, `opencode_worktree_remove`, …), its `~` expansion and its `mcp.servers` are read. `-openmoat` (or `-*`) in OpenCode 2's `plugins`, or a policy denying the plugin, makes `openmoat status` and `openmoat doctor` report OpenCode as not protected (the person's own `opencode.json[c]`) or warn about the project; the default policy denies the agent setting `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG` or `OPENCODE_CONFIG_CONTENT`, writing OpenCode 2's `service*.json`, and running `opencode plugin add|remove|update` or `opencode service set|unset`. With `OPENCODE_CONFIG_DIR` set, `openmoat init` installs the plugin there, which both versions load. OpenCode before 1.3.4, which loads no object plugin, is no longer set up: `openmoat status` says to upgrade ([#673](https://github.com/crocodile-labs/openmoat/pull/673)).
