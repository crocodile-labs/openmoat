### Added
- `openmoat run` takes a snapshot of the project's files before the agent starts and after it exits, into OpenMoat's own store outside the project (`--no-snapshot` opts out, recorded); `openmoat restore` puts them back after showing each change and asking, and takes an undo snapshot first; `openmoat snapshot` takes, lists (`--list`) and prunes (`--prune`) them. Secrets and other paths a deny rule names, ignored files and files over 5 MiB are left out and named; both commands are person-only, and the default policy denies them, and reading or changing the store, to agents (ADR-085) ([#789](https://github.com/crocodile-labs/openmoat/pull/789)).
- A snapshot holds each file's bytes as they are and a restore writes back those bytes, whatever the project's `.gitattributes` say: line-ending conversion (`text`, `eol`), `ident` and `working-tree-encoding` are off in OpenMoat's store, so a `.gitattributes` an agent plants can neither change what comes back nor make a snapshot fail ([#789](https://github.com/crocodile-labs/openmoat/pull/789)).
- Every `openmoat run` records its own start snapshot, even when the files are as the previous snapshot holds them, so a plain `openmoat restore` goes back to the start of the last run and never undoes an earlier run's work as well ([#789](https://github.com/crocodile-labs/openmoat/pull/789)).
- Two `openmoat run` in one project, or a run beside a person's `openmoat snapshot` or `openmoat restore`, no longer race on the snapshot store: taking, pruning and restoring hold the store's lock, each snapshot is staged in its own index file, and pruning drops only unreferenced files older than an hour ([#789](https://github.com/crocodile-labs/openmoat/pull/789)).
