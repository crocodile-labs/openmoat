### Security
- Windows: the new `wsl-crossing` deny rule stops an agent from handing work to the Windows Subsystem for Linux, where no Windows path rule reaches: `wsl`, `wslg`, `wslconfig`, `bash.exe` in the system folders and the listed Store distribution launchers, read as Windows reads a path, also as the program of a `cmd` or PowerShell line or in a `start` line; any word or path naming the `\\wsl$` or `\\wsl.localhost` share, the `\\?\UNC\` and `GLOBALROOT` forms included; and copying the launchers. A `cmd` or PowerShell line beyond simple commands (a variable, a bracket, a block, a call operator in PowerShell; `^`, `%`, `!`, `for`, `call` in `cmd`), or one naming `wsl` or `bash` anywhere, needs review ([#805](https://github.com/crocodile-labs/openmoat/pull/805)).
- Windows: `openmoat init` gives the state directory an access list of your account and `SYSTEM` only (inheritance off, every other entry removed, through `icacls.exe` by absolute path) and refuses a state directory another account owns; `openmoat doctor` reads the owner and list back and names any other account that may change or read it. It keeps other accounts out, not the agent, which runs as you; `doctor` says so ([#805](https://github.com/crocodile-labs/openmoat/pull/805)).
- Windows: `openmoat doctor` shows which Windows sandbox mode Codex's `config.toml` selects, and warns under `unelevated`, which does not enforce OpenMoat's read denies; it names WSL2 as the way to OS confinement where WSL is installed, and says under WSL1 that `openmoat run` needs WSL2 ([#805](https://github.com/crocodile-labs/openmoat/pull/805)).
